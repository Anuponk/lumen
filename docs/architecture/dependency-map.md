# Dependencies and data flow

Confirmed victory: before-scope projection → existing receipt/outcome → current
scope comparison → one celestial result (global > Adventure > constellation).
Badge additions → owner/catalogue-scoped ephemeral playhead → visible Mon ciel
background. SVG failures return to ordinary actions; rendering/skip/navigation
cannot write rewards. Actual geometry remains owned by the licensed atlas.

Existing-account ownership handoff: verified profile + archived previous attempt
→ one live progress object → `nextCanonicalQuest` (catalogue origin/access)
→ `resumeHydratedCampaignSelection` → existing grid/tutorial initialization.
No completion, reward or wallet mutation is part of selection.

Same-owner idle board → READY/campaign/no-start/empty-cell guard → origin frontier
comparison → exact attempt backup → normal board initialization. Started, replay
and already-correct selections stop before archival or navigation.

Guest first gesture: `ensureAttemptStarted` → start-only performance timestamps →
shared strict `isAttemptStartPerformance` → guest coverage exception only without
acquired facts → verified original profile/attempt archives → existing cloud
installation. No guest timestamp is imported into account reward/cooldown state.

Virgin-browser restore: empty unowned guest cache → exact original backup →
`guestNeedsReconciliation` checks acquired evidence without starter reserve or
current-origin defaults → verified existing cloud → owner-bound installation.
Guest play during hydration is rechecked; genuine spending/acquisitions still
use conservative coverage. No server, receipt or wallet writer changes.

Player-favorable recovery: same-owner hydration refusal → verified originals →
`cloud-profile.js:reconcilePlayerAcquisitions` → expected-account RPC with snapshot
row lock/CAS → positive projection merge and private source archive → independent
read-back → cache and one live UI progress object → mirror verification and flush.
Wallet/daily operations and pending-intent acknowledgement keep their existing
authorities. See the cloud contract for interpretation and release boundaries.

Historical queued recapture: UI `recoverQueuedLegacyReceipt` reads the original
expected-account receipt and current profile through `legacy-command.js`.
`durable-canonical-outbox.js` calls its strict duplicate proof, archives exact
evidence, then retires the original pending copy through the transactional cache.
The cache retires its paired navigation row; no server command is emitted.

Optional story (#532): startup eligibility → first-welcome local presentation
marker → game-screen supplies catalogue-first astronomical SVG → inert overlay
and narrative clock → release/focus on the same actual learning board. Aide replay
uses existing pause, never loadPuzzle/reset or a reward path. Context changes
cancel the presentation; no dependency on cloud readiness or command dispatch.
Explicit story/replay action → intro-music local Web Audio context; presentation
pause/exit → synchronous silence and context close. Audio refusal stays local.

Private QA structure: `scripts/recette-schema.mjs` consumes reviewed structural
metadata, emitting only `lumen_recette` objects plus whitelisted catalogue reads.
The restricted runner owns QA tables/functions; synthetic SQL claims never grant
shared Auth access. Cohort activation is admin-only, with reviewed release digest,
durable activation and a default-closed emergency stop. Guest capability 0 selects
compatibility before mutation. See the [runbook](../CLOUD_RECOVERY_391.md#private-schema-recipe-and-activation-control-24-october-2026).

Historical initialization: game-screen.js supplies original guest bytes and
session guard → cloud-profile.js → guest-claim.js (capture/discovery/receipt) →
private SQL guest_claim_receipts. Existing initialize is used only after an
explicit missing-capability discovery, never after ambiguous command emission.
historical-inventory.js reads cloud field/coverage contracts without mutating them.
rollout-gates.js and its CLI only evaluate operator evidence; sync_cohorts has
no browser writer. No SQL retirement/deletion dependency is introduced.

Persistence lot 3: gameplay-sync.js derives ephemeral domain readiness from a
current verified account/client/generation completion list. catalogue-access.js
and both UI access adapters isolate acquired replay from Wallet-only holds;
spending and pending-reward proofs remain guarded. Confirmed command results use
transactional-command-cache.js installAndRead before UI application; historical
startup readers remain compatible. Required coverage: gameplay-domain-tests.mjs,
Legacy UI tests and domain-replay-browser.mjs in the account browser suite.
See the cloud contract and PROGRESSION.md for proof and rollback boundaries.


Persistence lot 2: UI command imports → coordinated-command-adapters.js →
persistence-coordinator.js → existing Canonical/Legacy/Wallet proof adapters.
transactional-command-cache.js uses indexed-outbox-store.js version 1 to pair
immutable intentions with pending metadata and mirror owner-bound verified
profiles. Legacy UI cache reads remain active. Tests: persistence-coordinator-tests.mjs
and transactional-command-cache-browser.mjs (account-session browser suite).
Shadow instances inspect only; same-origin Web Locks serialize updated tabs.
See the cloud contract for fallback, authority and rollback limits.


Persistence foundations (lot 1): local.js returns verified durable results and
quarantines malformed bytes before replacement; game-screen.js reports refusals
and scopes hydration to account/client/generation, including rejected awaits.
profile-size.js owns the UTF-8/JSONB size boundary. Required checks:
local-persistence-contract-tests.mjs and cloud-hydration-generation-tests.mjs.
No reward authority, command identity or outbox format changes.

Reviewed recovery: account file choice → captured owner/client →
`approved-device-recovery.js` exact snapshot digests → expected-account restore →
acquisition coverage → verified exportable originals → second cloud read →
local installation and reload. No cloud, attempt, reward or outbox writer.

Quest convergence (#522): catalogue definition → `quest-rules` / `quest-rewards`
→ active UI/onboarding/read view. Numeric reward adapters preserve old IDs.
Victory facts → existing durable canonical outbox → `quest-command` V2 → locked
server ledger/daily/wallet transaction → exact receipt + current profile read →
acknowledgement. Mutable `runPerformance` is separate from immutable first-win
evidence. Cloud restore adopts a covering server V2 summary, never creates one.
Social stable identity uses its own RPC; participation still bypasses campaign
writers. Admin metrics/timeline read stable identity under existing capability.

Installation quota: achievement plan → verified original → failed cache install
→ bounded verified archival → unchanged owner/session/local bytes → one retry.
Wallet receipt recovery → exact coverage predicate → two verified originals
(localStorage/IndexedDB) → unchanged owner/session/local bytes → cache install
→ guarded outbox acknowledgement. Full synchronization still needs server proof.

Guided correction: pointerdown on incorrect Guardian → existing correction and
save → suppress that gesture's compatibility click → next pointerdown releases
suppression immediately. Shared helper also owns long-hold click suppression.

Guardian hold: touch pointer → 500 ms recogniser / movement cancellation → live
cell/attempt/learning guards → normal cell action → existing history, mistake,
assistance and persistence. Pointer identity suppresses a release retargeted to
the pause mask. Moving hands off to exclusion drag; mouse/keyboard keep clicks.

Phase-2 investigation: existing admin capability/RPC → closed timeline projection
→ session/trace episodes → observed transitions, bounded detail alerts, reviewed
report/GitHub composer. Account/client/capability guard rejects stale results and
actions. Export never depends on accounts/profiles or live gameplay objects.

Optional diagnostics (#534): guarded capture → separate bounded queue → Auth and
closed-schema batch → consent-locked private details → existing cockpit guard.
The existing operator cron prunes bounded details/budgets/resolved old health.
No save/receipt/profile dependency or competing live incident/alert algorithm.

Storage maintenance: account diagnostic → aggregate local/IndexedDB/browser
inventory; explicit maintenance → retain recent copies → exact original in
existing IndexedDB recovery store → committed read-back + session/source recheck
→ local removal. Export includes the archive. No profile/RPC/reward mutation.

Achievement backup quota (#536): verified server achievements + unchanged local
profile → shared recovery planner → verified localStorage or IndexedDB original
→ session/owner/local-byte recheck → achievement-only cache installation.
Explicit recovery export reads both IndexedDB snapshot stores. Wallet and full
hydration holds retain their existing authority and release conditions.

Completed quest presentation (#537): confirmed progress + existing availability
decision → completed card/history + explicit replay hold. Renderers never write
the profile or change catalogue, pack, Auth or hydration guards.

Hydration #536: selected verified snapshot → existing reconciliation refusal →
classified wallet/reward/storage diagnostic and safe hold. Final mirror result →
account/client recheck → current-session presentation only. Diagnostic formatting
never supplies proof for a reward merge or wallet acknowledgement.

Session recovery #530: verified server profile → canonical badge coverage →
safe local install or protected partial recovery. Unconfirmed wallet/canonical
operations stay in their durable stores. Classified local failure → account
status and existing `hydration_reconciliation` telemetry (fixed reason only).
No new RPC, Auth configuration or persisted profile field.
