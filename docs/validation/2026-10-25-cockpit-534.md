## Sources and scope

Production reads inspected only function definitions, schema and permissions;
no player profile, save, event payload or Auth account was queried. The source
audit is in [OBSERVABILITY_534](../OBSERVABILITY_534.md). All executable fixtures
use synthetic names, dates and accounts. SQL fixtures are transactionally rolled
back in the disposable PostgreSQL CI database; never run them on Supabase.

Activity remains qualified as *recorded analytics*, because passive openings
are included. Auth is `auth.users.last_sign_in_at`, scoped to Lumen accounts.
Domain dates come from immutable server receipts and mean committed operations,
not browser ACKs or current full sync. A missing receipt is not a failed save.
Session timelines do not invent temporal links between Auth, analytics,
diagnostics or command commits. Unknown platform/version/time stays explicit.

## Operational impact

No external service or recurring job. One batch of at most 250 date keys on
refresh and one session RPC per selection. Latest-receipt and event reads have
supporting indexes; no per-row frontend requests. Responses are bounded, while
index creation still needs a deployment window appropriate to actual table
sizes. No production volume, query latency or real billing was measured.
No telemetry TTL/consent/quota change, player rewrite, repair, backfill or receipt
deletion. Existing alerts and collector ownership stay unchanged.
