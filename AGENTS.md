# LUMEN — Codex workflow

## Locate before reading
- Start with `git status --short`, the symptom and affected invariant. Use [feature-map](docs/architecture/feature-map.md) to select modules, then relevant rows of [dependency-map](docs/architecture/dependency-map.md) and [test-map](docs/architecture/test-map.md). Do not load all maps by default.
- Follow the eight steps in [debugging-guide](docs/architecture/debugging-guide.md). Search symbols/references with scoped `rg -n`; discover paths with `rg --files`. Read bounded excerpts, then recent `git log`/`git show` for those paths. Broaden only when evidence requires it.
- Confirm root cause with a reproduction, assertion or trace before corrective edits. Distinguish hypotheses from confirmed causes; reuse verified [bug-history](docs/architecture/bug-history.md) entries.
- Match effort to complexity. No parallel agents for simple work. When delegation is justified, assign disjoint investigations and share evidence instead of repeating reads.
- Preserve useful context: keep short notes of inspected paths, symbols, evidence, decisions and remaining questions. Re-read only changed/newly relevant excerpts. Transfer durable findings to repository documentation with a Git reference.
- Keep detailed logs in local temporary files outside tracked sources; show only relevant errors and a short result. Never include credentials, personal data or player saves. Distinguish mocks, browser checks and live validation; report only tests actually run.

## Preserve contracts
- Before changing behavior, read relevant sections of [preserved agent contracts](docs/AGENT_CONTRACTS.md) and the owning product document. These remain mandatory; relocation does not weaken them. Investigate code/document disagreements.
- Preserve player data, stable IDs, rewards and active attempts. Catalogue metadata owns counts/order/boundaries/completion; never hardcode gameplay totals. The UI owns one live board/progress object; injected callbacks must read current state.
- **Cloud persistence — blocking invariant:** before auth, persistence, progression or commerce edits, read [cloud contract](docs/DATA_AND_ARCHITECTURE.md#cloud-persistence-contract) and [cloud regression matrix](docs/TESTING.md#cloud-persistence-regression-matrix). Never overwrite newer cloud progress with stale local state. Offline data remains pending until acknowledged; server transactions/entitlements remain authoritative.
- Consult [GAMEPLAY](docs/GAMEPLAY.md), [PROGRESSION](docs/PROGRESSION.md) and [UX](docs/UX_AND_VISUAL_DIRECTION.md) for affected rules. Preserve same-run badges, challenge isolation and teaching milestones. Changes to rules, assistance, eligibility, gestures, progression, navigation or terminology require the onboarding impact check in the preserved contracts.
- **Astronomical source of truth — mandatory for all new content:** Never invent or hand-draw star coordinates. Generated content must meet [GRID_CATALOG](docs/GRID_CATALOG.md) and [astronomical generation](docs/GENERIC_ASTRONOMY_RENDERER.md) contracts: valid, unique, explainable grids, licensed real astronomical references and compatible saves.

## Validate and deliver
- For applicable bug fixes: reproduce with a business-behavior regression test, run it and confirm the expected failure, identify the root cause, fix the code, then confirm the test passes. Run neighboring tests and required pre-PR checks. After two similar failures, re-examine the diagnosis instead of stacking empirical fixes. Never weaken a test to obtain a pass; a broken fixture needs contract evidence and replacement coverage of both cases.
- Use `npm run test:affected` (or `node scripts/test-affected.mjs`) during corrections; inspect `--list` when needed. Group related fixes, retain only useful error output, and do not repeat unchanged validations without new evidence. Run `npm run test:full` before PR for this test tooling and whenever impact is uncertain; targeted success does not replace applicable browser/SQL/manual requirements. See [local selection](docs/TESTING.md#local-affected-tests-phase-2).
- Every code/gameplay/feature change updates its test contract in the same change, retaining regressions. Gameplay changes require complete in-app `runHintTests()` and strict catalogue audit; see [TESTING](docs/TESTING.md) for applicable commands and other mandatory checks. Board input changes require mobile tap/drag verification.
- Documentation-only changes require path/link checks, contract-preservation review and `git diff --check`; do not claim unexecuted runtime validation. Maintain maps when ownership/entry points/commands change, without duplicating product contracts.
- Complete the PR template's cloud-impact section; include Onboarding impact, actual validation and outstanding limits. Keep summaries short and evidence-based.
- Never merge without explicit user authorization. A push is not proof of production release; follow [RELEASE](docs/RELEASE.md), report the SHA and verify the intended deployment when releasing.
